# Design Knowledge System

Use this system to carry a design discovery from official evidence to an exact
screen without turning one app decision into a universal rule.

## Ownership And Overlap

| Surface | Owns | Does not own |
|---|---|---|
| Design Operating System | Global philosophy, judgment questions, evidence readiness, authority and verification invariants | Volatile platform facts, production code, final QA disposition |
| Design Task Packs | Flow, visual/accessibility, and implementation-review procedures for a selected task | A second copy of platform guidance or app tokens |
| iOS Platform Knowledge | Curated current Apple sources, contextual interpretation, applicability, exceptions, strength, conflicts and recheck triggers | App intent, exact token values, dependency approval, automatic activation |
| Product Design Audit | Screenshot-bound journey and flow evidence | Normative Apple guidance, code behavior, full accessibility compliance |
| build-ios-apps skills | SwiftUI implementation patterns, simulator/debugger evidence, performance and platform API technique | Product hierarchy, Design authority, app-local exception approval |
| App-local contract | Exact tokens, numbers, selected exceptions, implementation references, candidate, oracle and visual-QA completion criteria | Silent global overrides or unsanitized cross-app generalization |
| QA/Release and the assigning lead | Exact-candidate verification evidence and final disposition | Product intent or implementation ownership |

## The Required Flow

1. **Official source.** Bind the current primary URL, access date or change
   marker, platform scope and paraphrased source basis. A local record proves
   only what was checked at that time.
2. **Application context.** Name the component, task, device, input method,
   content, state and conflicting guidance that make the source relevant.
3. **Product decision.** Select the direction, strength, exception, owner,
   recovery and reversal evidence. Do not let the source make the product
   decision by itself.
4. **Implementation token or pattern.** Put exact values, units, component
   roles and implementation references in the app-local contract, not in the
   platform source.
5. **Matching-surface verification.** Bind the exact candidate, approved
   intent, oracle, environment, scenarios and evidence. Report match,
   deviation or unknown; do not infer completion from a guideline citation.

## Runtime Use

The static manifest pins `current-source:design:ios-platform-knowledge` to the
checked-in bytes. For a material iOS decision, the Sejong lead rechecks the
applicable official pages and supplies those exact bytes through a parent-issued
`runtime_reference_set`. The source is conditional evidence; it is not added to
every Design job's kernel and Task Pack selection.

The read ledger can prove which local bytes were materialized and marked used
or unused for one job. It does not prove that the live Apple page was refreshed
automatically or that the worker applied the guidance correctly. Preserve that
limit in every handoff.

## Freshness And Conflicts

- Recheck before a material decision when the target OS, SDK, component,
  device, input method, content model or applicable HIG change log differs.
- Correct a demonstrably wrong official-source record after direct
  verification and regression checks; do not wait for repeated app runs.
- When current official sources appear to conflict, identify their precise
  scope first. In particular, keep visible size, effective interaction region,
  default size and exceptional minimum as separate concepts.
- Keep unresolved conflicts explicit. Use a reversible local decision or
  return to the authorized decision owner; never collapse the conflict into a context-free slogan.

## Promotion And Re-entry

An app-local token or exception remains job-bound. Upward promotion needs
sanitized evidence from at least three independent runs, a proposal with no
activation authority, paired no-regression evaluation, shadow use and explicit
approval. Source corrections use the faster evidence-correction path.

Do not create a standalone iOS Design skill unless observed work demonstrates
a distinct intake, workflow, output and stop condition plus routing or context
cost that a Current Source Set cannot solve.
