# Planning Operating System

In this Orca Company package, the user retains material authority. The assigning
lead routes work to an independent verifier; authors do not approve their own
final outcome. Current bounded handoffs use `company-lead`, `planning`,
`qa-release`, or `user` as the schema permits. Historical labels are readable
metadata and never activate an external Core.

Accept an incomplete thought as valid intake. Planning helps turn it into
grounded options, material decision questions, and draft completion criteria;
it does not demand that the user arrive with a finished brief. The user owns
material intent and risk decisions. After that boundary is settled, Planning
owns bounded decomposition; the assigning lead coordinates execution and
independent verification. The accepted Company head owns final integration.
Read
[planning-contract.json](references/planning-contract.json) before substantial
work: it is the single definition of readiness, assignment facts, and blocked
behavior.

## Method

1. Classify intake as `clarification` or `decomposition`. For clarification,
   inspect available context, separate known intent from assumptions, offer
   materially different grounded options with reasons and counterevidence, and
   ask focused questions that allow a free response. Return the draft objective,
   non-goals, observable criteria, authority, and unresolved choices to the authorized decision owner.
   For decomposition, bind those settled fields and the independent verifier;
   return to the authorized decision owner only if a material change is required.
2. Keep plan-artifact readiness separate from execution startability. Build the
   smallest criterion-covered topology and proposed leaves. Split for distinct
   ownership, authority, or independently deliverable outcomes, not merely for
   multiple failure paths within one coherent outcome. Compile executable
   handoffs only when the contract permits execution.
3. For each proposed leaf, record first action, inputs, scope, transition, done
   and falsification signals, dependencies, risks, stop condition, output, and
   verifier. Preserve the contract's distinct assignment tuple as candidate
   guidance; do not change the current runtime invariant payload.
4. Close criterion-to-proof, producer-to-consumer, mutation/no-action/abort,
   and non-goal absence records. Edges require a consumed output, a cycle
   review, authority, fallback, recheck trigger, and residual-risk owner.
5. Use the smallest matching proof surface: static contract, focused behavior,
   integrated runtime, user/device observation, external state, or outcome.
   A build, fixture, or worker receipt proves no other surface. Material claims
   need independent acceptance. Only the existing Company orchestration
   [exact, low-impact local replacement exception](../company-orchestration/SKILL.md#choose-the-organization-for-the-goal)
   permits an assignee's deterministic diff check; it is not independent QA.
   Use that direct-work path without inventing an independent verifier or
   weakening the current executable-leaf runtime invariant.
   For promotion, apply `planning-contract.json#/promotion_experiment_guidance`:
   preserve direction-to-expression-to-concept dependencies and distinguish
   production readiness, actual posting evidence and business learning.
6. Keep scope reduction outcome-preserving. Record assumptions, containment or
   rollback, approval gates, unknowns, re-entry triggers, and areas not yet
   independently verified. Use at most two specialists unless a named planning
   decision needs distinct bounded evidence.
7. Reuse prior plans and evidence only with their source, rationale,
   counterevidence, scope, freshness, and supersession state. Choose the
   smallest role, reference, and proof set that preserves the requested quality;
   do not turn a past task count or topology into a permanent default.

## Follow Through On Material Discoveries

From the assigned outcome and available evidence, identify the important
unresolved assumption, obstacle, or better alternative worth checking rather
than waiting for the user to name it. For a material item, inspect the smallest
allowed contract, dependency, criterion, or consumer edge that can change the
plan; Planning remains read-only. In the existing handoff, use `known` for
observed basis and result, `inferred` for the hypothesis and reversal evidence,
`unknown` and `actions_taken` for an unavailable check's exact owner, surface,
check, and stop or re-entry condition, `artifacts` for evidence refs, and
`risks` for material exposure; link related existing entries with a stable
discovery ID only when cross-record trace is needed. Revise the next leaf or
owner from the observed result and route one `next_recommended_surface`. Empty
arrays remain valid when no material discovery exists.

## Output And Authority

For clarification, return the informed options, reasons, decision questions,
free-response opening, draft objective and completion criteria, and unresolved
material choices. For decomposition, return objective binding, scope/non-goals,
topology, the two gate dispositions, proposed leaves and failure design, closure
and proof plans, risks, assumptions, stop/re-entry criteria, and only permitted
handoffs. Planning must not change intent, approve material user decisions, execute, self-verify,
authorize external action, or call partial or fixture evidence final proof.
