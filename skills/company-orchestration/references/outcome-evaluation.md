# Saved outcome evaluation

Use `scripts/outcome_eval.py` when an approved evaluation needs frozen inputs and
objective grading of saved outcomes. This is optional evaluation tooling, not a
new per-task ritual, execution engine, identity service or approval gate. The
operator still uses actual Orca Task/Dispatch commands and the worker's injected
preamble. Do not launch Core, create a second Run, retry uncertain actions or
change provider billing through this tool.

## Evidence and comparison boundary

The first supported study is a **feasibility/data-path pilot**: two tasks, two
repeats, baseline and candidate, eight fresh actual Dispatches. It checks whether
instructions can be supplied, isolated task files changed with real local tools,
receipts collected and saved outcomes regraded. It cannot establish statistical
superiority, noninferiority, portfolio quality, lower user burden or token savings.
The third supplied task is available for a separately frozen future pilot.
For that first pilot, the frozen `expected_trials` array records order: repeat,
task, baseline then candidate. That feasibility order is fixed and not randomized. Do not infer a
causal effect from it; preregister randomization/counterbalancing for a later study.

Only the supplied instruction snapshot varies by arm. Route, observed agent ID,
model/effort, context snapshot, task/input/oracle, tools, authority, receipt
collection, timeout, worker cap and retry policy are common. Receipt projection
automation is a separate intervention; keep it the same in both instruction arms.
For a receipt experiment, freeze another plan with identical instructions and
assess entry errors/work separately. Do not attribute a combined change to either
component.

Fresh sessions do not remove host-injected AGENTS, global instructions, memory,
skills, Stop hooks, provider context or backend changes. Capture the common
observations and unknowns before freezing. A supplied-text comparison does not
prove clean-room Company loading or isolate installed hooks. Launch model/effort
fields are captured route selection; they do not authenticate live provider
identity. Record any later observed mismatch and do not silently pool it.

The earlier proposal for a future effects study used six task families
(planning, design, development, research, deployment/recovery, combined handoff),
two tasks each, five repeats and two arms: **120 proposed runs**, not completed
runs or a mandatory next-study size. Freeze task-level paired analysis, stopping rule, minimum meaningful effect,
critical failures and sample-size reasoning before that study. Reuse the audit's
paired task-cluster bootstrap and all-success `C(s,k)/C(n,k)` method; do not count
repeats as independent task clusters. This feasibility CLI deliberately emits no
confidence interval or superiority decision.

### Optional six-task descriptive study

`assets/outcome-eval/tasks-next.json` supplies six synthetic outcome tasks:
`planning-open`, `planning-settled`, `evidence-conflict`, `candidate-handoff`,
`recovery-unknown` and `development-state`. Five grade structured semantic
decisions; one grades a state reducer. All preserve protected input bytes.
Author-side counterexamples are in `scripts/test_company_outcome_tasks_next.py`;
their passing does not replace independent task/oracle acceptance before runs.

A separately accepted plan can use two arms and two repeats for **24 descriptive
trials**. Its hash-bound `context.execution_order` is the preregistered actual
schedule; `plan.expected_trials` remains the balanced inventory generated by the
unchanged v1 CLI. Independently verify identical IDs/task/arm mappings, within-task
sequential pairs and reversed second-repeat order, then compare actual launch
timestamps with that schedule. The CLI does not enforce chronological execution.
Keep every planned slot in the denominator, preserve unknowns and failures, and
use no automatic retries. The 600-second observation boundary does not establish
process exit. Freeze task/oracle bytes before execution; do not repair difficulty
after seeing results. Keep this study separate from the older Luna-medium pilot.
It detects bounded regressions and observes captured executor tokens; it does not
establish superiority, noninferiority, calibrated usability or whole Company quality.

## Files and frozen manifest

`assets/outcome-eval/tasks.json` contains three generic versioned tasks:

| Task | Real local action | Objective oracle |
|---|---|---|
| `boundary-repair` | Edit a Python interval predicate while preserving a user original | Eight boundary/missing/reversed/custom-threshold function cases, exact boolean type, protected-byte and file-inventory checks |
| `evidence-reconcile` | Read raw event files and create a reconciliation artifact | Exact JSON final state; globally unique Dispatch, nonzero/unknown exits, missing trial denominator, input preservation |
| `recovery-readback` | Reconcile saved candidate/timeout readback into a local recovery artifact | Exact JSON; no approval transfer, success claim or duplicate retry; original preservation |

The coordinator supplies only the prepared brief and task directory to each
worker. Do not give the executor expected answers or another trial's transcript.
Oracle files are available to the evaluator and independent reviewer. This is an
instruction boundary, not a filesystem security sandbox; tools cannot certify
that an executor never inspected an answer.

`freeze` creates a new bundle and refuses an existing output directory. Its
manifest includes exact task specs, initial bytes, objective oracle, expected
trial inventory, grader hash, source reference, common conditions and instruction
file hashes. The printed SHA-256 is the caller's immutable plan anchor. Keep it
outside the mutable bundle in the accepted private study record. All later
commands require this exact anchor. Changes require a new plan; never rehash a
changed plan and continue counting the old trials. The tool does not provide
write-once storage, signatures or an authentication service.

The source reference identifies the source baseline; it does not assert a clean
checkout or replace the exact frozen instruction bytes. Freeze after source QA
because changing `outcome_eval.py` invalidates its pinned grader hash. Do not copy
the audit's historical 166-artifact fixture tree into production.

## Commands

Run with the project's compatible runner. This standalone script has no third
party dependencies and requires Python 3.13 or newer. Confirm the interpreter
once with `uv run --no-project --python 3.13 python -c 'import sys; print(sys.executable); print(sys.version)'`.

Prepare approved baseline/candidate instruction files and a context file copied
from `assets/outcome-eval/context.template.json`. Fill observed fields; leave
unavailable fields null. Use identical file ordering/headers in both instruction
snapshots. For the initial pilot, freeze only the two default tasks:

```sh
uv run --no-project --python 3.13 python -B skills/company-orchestration/scripts/outcome_eval.py freeze \
  --spec skills/company-orchestration/assets/outcome-eval/tasks.json \
  --baseline /private/study-inputs/baseline.txt --candidate /private/study-inputs/candidate.txt \
  --context /private/study-inputs/context.json --source-commit ACCEPTED_SOURCE_SHA \
  --agent OBSERVED_ENVELOPE_AGENT --model OBSERVED_SUPPORTED_MODEL --effort OBSERVED_SUPPORTED_EFFORT \
  --tasks boundary-repair,evidence-reconcile --repeats 2 --evidence-class real \
  --out /private/frozen-study
```

The paths and uppercase values above are examples, not executable evidence. Keep
the printed `plan_sha256` in the study record. For each expected trial, `prepare`
creates a new exact task directory and a brief outside its writable files:

`--agent` is the exact opaque agent ID observed in both launch selection fields,
not an inferred CLI alias (for example, an `agy` launch may report `antigravity`).
Omit `--effort` only when that route reports unsupported effort as null; the plan
preserves null and checks it exactly. Both arms use one route/model/effort.
Do not mix Codex and Antigravity results after a capacity failure or silently
substitute settings. Freeze a separate plan for the newly selected route.

```sh
uv run --no-project --python 3.13 python -B skills/company-orchestration/scripts/outcome_eval.py prepare \
  --plan /private/frozen-study/plan.json --plan-sha256 FROZEN_PLAN_SHA \
  --trial boundary-repair-baseline-1 --workspace /private/trial-artifacts/boundary-repair-baseline-1
```

The coordinator launches a **fresh** worker with the printed brief verbatim,
using the existing Run and actual supported Orca command. Maximum two workers
total; never exceed another task's tighter cap. Save raw launch response and
actual worker_done. A launch `outcome_unknown` does not justify a replacement;
inspect that same Dispatch and let its actual valid worker_done settle it.
Capture original trace/tool evidence, final artifact files and available raw
usage. Do not require worker shell exit: shell liveness is not task completion.

`collect` snapshots artifacts and receipts into `trials/<trial-id>/`, without
altering originals. It rejects another collection under that trial ID. Missing
done/trace can be collected honestly and remain unknown. A launched failure,
abort or environment failure stays in its originally planned arm.

```sh
uv run --no-project --python 3.13 python -B skills/company-orchestration/scripts/outcome_eval.py collect \
  --plan /private/frozen-study/plan.json --plan-sha256 FROZEN_PLAN_SHA \
  --trial boundary-repair-baseline-1 --workspace /private/trial-artifacts/boundary-repair-baseline-1 \
  --brief /private/frozen-study/briefs/boundary-repair-baseline-1.txt \
  --launch /private/receipts/launch.json --done /private/receipts/done.json \
  --trace /private/receipts/tool-trace.txt --status success
```

The raw launch schema is the current successful Orca envelope containing
`result.runId/taskId/dispatchId`, `result.launch.requested/effective` and one
agent terminal effect. A raw done send receipt contains `result.message`; a
raw coordinator inbox contains `result.messages`. Keep the entire unmodified
inbox receipt: the grader selects exactly one worker_done for the bound Task or
Dispatch and rejects duplicate/conflicting same-task rows. Unrelated task mail
is allowed. The selected message's Run, sender, Task and Dispatch must match the
launch. Message payload may be JSON text or an object. Do not rewrap a message
into a fabricated raw receipt.

The prepared brief asks the worker to report actual edited paths through its
real preamble's `--files-modified`. The grader normalizes relative or absolute
in-workspace `filesModified` and compares them with the frozen initial/final
artifact difference. Missing claims remain unknown; stale/outside/mismatched
paths are invalid. This binds declarations and bytes, not authorship or identity.
Both arms also explicitly require Python `-B` or `PYTHONDONTWRITEBYTECODE=1` for
local checks, so incidental `__pycache__` does not violate the artifact scope.

`collect` prints a hash-bound `review_template`. The independent reviewer inspects
raw source/provenance, tool authority, final files and critical risks, fills
`assessor`, `critical_failure` and `note`, then saves it as
`trials/<trial-id>/review.json`. All binding fields must remain exact. `assessor`
must differ from the captured executor. For real studies, `basis` must be
`independent`; unit-test fixtures use `synthetic_fixture`. These are checked
declarations, not proof of real identity or independence. No calibrated open
quality or user-burden grader is supplied, so those fields stay null.

```sh
uv run --no-project --python 3.13 python -B skills/company-orchestration/scripts/outcome_eval.py score \
  --plan /private/frozen-study/plan.json --plan-sha256 FROZEN_PLAN_SHA --allow-task-code
```

`--allow-task-code` explicitly authorizes executing the saved trusted Python task
artifact for its function cases, in a temporary current directory, with isolated
Python flags and a five-second timeout. This is **not an OS sandbox**; review
untrusted artifacts before enabling it. Without the flag the code task stays
unknown. JSON tasks need no code execution. Regrading never launches agents or
external services; trusted code execution may have effects if the code violates
its authority, which the tool cannot prevent.

## Grading and failure preservation

Every planned trial remains in its original denominator. Missing and unknown
trials make the ordinary task success rate null; the confirmed-success lower
bound remains successes/planned. Failure, environment failure and abort are
retained. Task macro means give equal weight to each task. All-success-k is
`C(successes,k)/C(planned,k)`, not pass@k; it is null with incomplete outcomes or
fewer than k repeats.

Success requires matched actual done, passed final-state oracle, captured trace
and edited-path binding, plus an independently declared no-critical-failure review bound to the exact
artifacts/candidate/conditions/Dispatch. A nonzero Python oracle exit fails.
Absent done or unexecuted/timed-out code oracle stays unknown. Protected input
loss or an unexpected artifact is a deterministic critical failure; broader
critical risk remains the independent reviewer's responsibility. A critical
failure blocks the gate regardless of averages. Review bindings cannot be reused
after artifact changes.

Dispatch IDs are globally unique across all observed trials. Relabelling Run,
Task, trial or receipt filename cannot count the same actual Dispatch twice.
Different Dispatches for the same host Task remain different attempts. Hash,
candidate, context, tool-condition or lifecycle mismatch is an invalid input,
never silently dropped from the report.

Exit 0 means **the supplied records were graded**, including failed/incomplete
studies. Read `gate`, per-trial statuses and unknown fields. `recorded_outcomes_graded`
is not a pass, installation effect or owner acceptance. Invalid input emits
structured JSON and exit 2. Saved-byte repeatability is distinct from rerunning
a probabilistic model. Unit tests fabricate receipts and remain synthetic;
using a real Orca envelope shape does not make them real execution evidence.

Optional `collect --usage usage.json` accepts:

```json
{"coverage":"partial","raw_total":null,"tokenizer":null,"scope":"executor only; lead/review/integration unavailable","source":"captured provider usage location or unknown"}
```

Keep original usage evidence in the private study. Coverage values are unknown,
partial or complete. Per-trial available raw totals are retained as reported;
the CLI does not certify non-overlap or whole-run coverage and never sums a
complete-looking set into end-to-end savings. Do not infer tokens from credits,
API prices, bytes, time or missing logs, or double-count cache/reasoning already
included in a provider total.

## Verification

```sh
uv run --no-project --python 3.13 python -B scripts/test_company_outcome_eval.py
```

The tests cover real-schema synthetic launch/done bindings, duplicate actual
Dispatch with renamed receipt/Run/Task, stale candidate/condition/review,
missing runs/done, nonzero exits, critical failure, original loss, unknown usage,
strict JSON and paths, grader drift and deterministic saved regrading. Source
tests prove these contracts only. Independent QA, actual pilot launches and
installation readback remain separate owned steps.
